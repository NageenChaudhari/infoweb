🔐 Secure Audit – WRONG ❌ vs TRUE ✅

1️⃣ INSERT Query

❌ WRONG (SQL Injection Risk)
  • User input directly concatenated
  • No validation
$name = $_POST['name']; $email = $_POST['email']; $sql = "INSERT INTO users (name, email) VALUES ('$name', '$email')"; pg_query($conn, $sql);
✅ TRUE (Secure – Prepared Statement)
  • Parameterized query
  • Input validation
$name = filter_input(INPUT_POST, 'name', FILTER_SANITIZE_SPECIAL_CHARS); $email = filter_input(INPUT_POST, 'email', FILTER_VALIDATE_EMAIL); $sql = "INSERT INTO users (name, email) VALUES (:name, :email)"; $stmt = $pdo->prepare($sql); $stmt->execute([ ':name' => $name, ':email'=> $email ]);

2️⃣ UPDATE Query

❌ WRONG
  • ID tampering possible
  • Dynamic SQL
$id = $_GET['id']; $name = $_POST['name']; $sql = "UPDATE users SET name='$name' WHERE id=$id"; pg_query($conn, $sql);
✅ TRUE
  • POST method
  • Validated ID
$id = filter_input(INPUT_POST, 'id', FILTER_VALIDATE_INT); $name = filter_input(INPUT_POST, 'name', FILTER_SANITIZE_SPECIAL_CHARS); $sql = "UPDATE users SET name = :name WHERE id = :id"; $stmt = $pdo->prepare($sql); $stmt->execute([ ':name' => $name, ':id' => $id ]);

3️⃣ DELETE Query

❌ WRONG
  • DELETE via GET
  • No CSRF protection
  • Injection risk
$id = $_GET['id']; $sql = "DELETE FROM users WHERE id=$id"; pg_query($conn, $sql);
✅ TRUE
  • POST only
  • Validated input
  • Secure execution
$id = filter_input(INPUT_POST, 'id', FILTER_VALIDATE_INT); if (!$id) { exit('Invalid ID'); } $sql = "DELETE FROM users WHERE id = :id"; $stmt = $pdo->prepare($sql); $stmt->execute([ ':id' => $id ]);

🔐 Additional Security Controls

  • Authorization check before UPDATE/DELETE
  • Transactions for data integrity
  • Least privilege database user
if ($_SESSION['role'] !== 'ADMIN') { http_response_code(403); exit; } $pdo->beginTransaction(); try { $stmt->execute(); $pdo->commit(); } catch (Exception $e) { $pdo->rollBack(); error_log($e->getMessage()); }

📜 Audit Note

Database INSERT, UPDATE, and DELETE operations are implemented using prepared statements with parameterized queries. Direct user input concatenation is avoided, preventing SQL injection vulnerabilities.

1. Authentication & Passwords

❌ WRONG
  • Plain text passwords
  • Weak password policy
password = 'admin123';
✅ TRUE
  • Hashed passwords (bcrypt)
  • Strong password rules
password_hash($password, PASSWORD_BCRYPT);

2. Authorization & Access Control

❌ Users access admin URLs directly /admin/delete.php?id=5
✅ Role-based access enforced if ($_SESSION['role'] !== 'ADMIN') { http_response_code(403); exit; }

3. Session Management

❌ Session ID reused, no timeout session_id($_GET['sid']);
✅ Secure session handling session_regenerate_id(true); ini_set('session.cookie_httponly',1); ini_set('session.cookie_secure',1);

4. Transport Security (HTTPS)

❌ HTTP allowed http://example.com/login
✅ HTTPS enforced RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [R=301]

5. Input Validation

❌ Direct user input $name = $_POST['name'];
✅ Server-side validation $name = filter_input(INPUT_POST,'name',FILTER_SANITIZE_SPECIAL_CHARS);

6. SQL Injection

❌ Dynamic SQL "SELECT * FROM users WHERE id='$id'"
✅ Prepared statements $stmt = $pdo->prepare("SELECT * FROM users WHERE id=?"); $stmt->execute([$id]);

7. Cross-Site Scripting (XSS)

❌ Output not encoded echo $_GET['msg'];
✅ Output encoding + CSP htmlspecialchars($msg, ENT_QUOTES);

8. CSRF Protection

❌ No CSRF token
✅ CSRF token validation $_SESSION['csrf'] = bin2hex(random_bytes(32));

9. Content Security Policy (CSP)

❌ Unsafe CSP default-src * 'unsafe-inline';
✅ Secure CSP default-src 'self'; script-src 'self'; frame-ancestors 'none';

10. Security Headers

❌ Headers missing
✅ Security headers enabled X-Content-Type-Options: nosniff X-Frame-Options: DENY

11. Error Handling

❌ Detailed errors shown
✅ Generic errors + logging ini_set('display_errors',0);

12. Logging & Audit Trail

❌ No logs
✅ User activity logged User | Action | IP | Time

13. File Upload Security

❌ Any file upload allowed
✅ File type & size validation $allowed = ['pdf','jpg','png'];

14. Database Security

❌ Superuser DB access
✅ Least privilege access GRANT SELECT,INSERT TO app_user;

15. Configuration & Secrets

❌ Credentials in code
✅ Env-based configuration

16. Rate Limiting

❌ Unlimited login attempts
✅ Login throttling enabled

17. Backup & Recovery

❌ No backup strategy
✅ Regular encrypted backups
